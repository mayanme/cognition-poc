# Internal Tools Platform — build-vs-buy prototype

## What this is

A **local-only demo** of an internal-tools platform, built in a single ~2-hour session to support a
build-vs-buy evaluation (low-code platform such as Power Apps vs. building with Devin) at a fintech.

The point it makes: a small **shared scaffold** (login, roles, audit log, layout) is written once, and each
new internal tool plugs into it. Tool #1 (KYC review) is real and enforces role-based decisions with an
audit trail. Tool #2 (Refunds) is a deliberately minimal read-only stub that exists to show a second tool
inheriting the scaffold for free.

**Honesty is a feature here.** Everything is fake seeded data. This app never touches real customer data,
has no real authentication, and is not deployable as-is. Every stub is labeled as a stub in the UI as well
as in the list below.

Stack: Next.js (App Router) + TypeScript, SQLite via `better-sqlite3`, server-rendered pages with Server
Actions for mutations. No cloud, no external database server, no Docker.

## How to run it

```bash
npm install   # installs dependencies (compiles better-sqlite3 locally)
npm run seed  # creates db/demo.sqlite and populates it with fake data
npm run dev   # http://localhost:3000
```

`npm run seed` is safe to re-run at any time — it wipes the demo tables (including the audit log) and
repopulates them, which is the easiest way to reset the demo between runs.

Other scripts: `npm run build`, `npm run lint`, `npm run typecheck`.

## The demo path

1. Open <http://localhost:3000> — the yellow banner at the top declares that the login is a demo stub.
2. **Pick a user** on the login page and sign in as a **viewer** (e.g. "Ada Viewer").
3. Go to **KYC Review**: the full applicant queue is visible, filterable by pending/all, and any applicant
   can be opened. The approve/reject buttons are **not** shown.
4. On an applicant page, use the clearly-labeled **"Force approve (expect 403)"** button. It submits the same
   Server Action a reviewer would, and the server refuses with a 403 message — enforcement lives on the
   server, not in the hidden UI.
5. **Switch user** (top right) and sign in as a **reviewer** (e.g. "Grace Reviewer").
6. Open a pending applicant, type a free-text reason, and **Approve**. The applicant's status, decider,
   timestamp and reason are persisted.
7. Open the **Audit Trail**: the decision appears at the top with actor, action, target and reason.

## Repo structure

```
scaffold/          shared, security-sensitive foundation reused by every tool
  auth.ts          DEMO STUB login: pick-a-user + session cookie
  roles.ts         requireRole(role) / requireUser() — server-side 403 enforcement
  audit.ts         logAction(...) + audit-log queries (append-only)
  db.ts            SQLite connection, applies db/schema.sql
  session-actions.ts  Server Actions for sign in / sign out
  layout/          shared nav shell + persistent demo-stub banner
tools/kyc/         Tool #1: queries, decision Server Action, decision form
tools/refunds/     Tool #2 (stub): read-only query
app/               Next.js routes; thin pages that call scaffold/ and tools/
db/                schema.sql + seed.ts (fake data); demo.sqlite is generated, not committed
```

Roles: `viewer` (read-only) and `reviewer` (can decide). `requireRole('reviewer')` runs inside the
`decideApplicant` Server Action, so an unauthorized decision fails server-side even if the UI is bypassed.

Every approve and reject writes an `audit_log` row via `logAction` (including the reason), alongside the
applicant status update. Demo-stub logins are logged too, so the trail is never empty during a demo.

## What is stubbed / faked (on purpose)

- **Fake login.** No passwords, no SSO, no identity verification: you pick a user from a seeded list and the
  chosen user id is stored in a plain cookie that anyone could edit. Labeled by a persistent banner on every
  page and again on the login page.
- **Fake data.** All users, applicants, risk scores and refund requests are generated by `db/seed.ts`.
  No real KYC records, documents, sanctions/PEP screening or PII of any kind exist in this app.
- **Refunds tool is a stub.** List view only, no actions, no refund logic. It exists to demonstrate scaffold
  reuse, and says so on the page.
- **Decisions are final.** No re-open / re-review workflow; a decided applicant cannot be changed.
- **No emails, notifications, integrations, file uploads or reports.**
- **Visual polish is minimal** — plain CSS, no component library, no responsive design work.

## What production hardening would require

- **Real authentication and authorization:** company SSO/OIDC, signed and expiring sessions, CSRF hardening,
  role assignment from the identity provider (not a seeded column), and least-privilege service accounts.
- **PII and data protection:** encryption in transit and at rest, key management, field-level access controls,
  data retention and deletion policies, and a privacy/DPIA review before any real KYC data is loaded.
- **A real database:** managed Postgres (or similar) with migrations, backups, point-in-time recovery and
  connection pooling instead of a local SQLite file.
- **Audit integrity:** append-only storage with tamper evidence, export to the central log/SIEM platform, and
  retention aligned to the relevant regulatory obligations.
- **Deployment and operations:** CI/CD, environment separation, secret management, health checks, metrics,
  alerting, and error tracking.
- **Testing:** unit tests for the scaffold (especially `requireRole` and audit writes), integration tests for
  the decision flow, and end-to-end coverage of the demo path.
- **Scale and usability:** pagination, search and sorting on every queue, bulk actions, four-eyes/maker-checker
  review, SLA timers, accessibility review, and a design-system pass.
